# Архитектурная передача командной почтовой системы

## Принятое решение

Использовать MailExpert 3.3.0 как веб-клиент и слой синхронизации. MailExpert — собственный форк upstream-проекта [MailFlow](https://github.com/maathimself/mailflow); его архитектура сохраняется так, чтобы полезные upstream-исправления можно было переносить после проверки. На первом этапе все рабочие почтовые ящики принадлежат одному общему пользователю MailExpert без прав администратора. Для управления системой создаётся отдельная учётная запись администратора.

Начальный объём — до 100 личных аккаунтов Gmail. Каждый Gmail подключается отдельным Google OAuth 2.0 consent flow; пароли приложений не являются основным способом подключения MVP. Собственные доменные ящики с доставкой через Microsoft EOP реализуются отдельным последующим этапом. Менеджеры работают с каждым ящиком отдельно; общая лента писем из всех аккаунтов не входит в MVP.

## Текущий статус реализации

Готов bootstrap: создан форк `wyrtensi/MailExpert`, выполнен пользовательский ребрендинг, перенесены два проверенных upstream-исправления IMAP, составлены карта кодовой базы и анализ PR. Google OAuth, полное обновление зависимостей, mailbox-first UI и EOP mail node пока не реализованы. Их порядок и критерии проверки находятся в `docs/superpowers/plans/2026-09-11-mailexpert-shared-gmail-mvp.md`.

## Что уже предоставляет MailExpert

- Несколько IMAP/SMTP-аккаунтов у одного пользователя MailExpert.
- Несколько одновременных браузерных сессий одного пользователя через Redis.
- Навигацию по отдельным почтовым ящикам и папкам.
- Поиск и быстрый переход к аккаунту через палитру команд.
- Флаг `include_in_unified_inbox` для каждого аккаунта.
- Отдельную SMTP-маршрутизацию и адреса-алиасы для каждого аккаунта.
- Локальный кеш сообщений и полнотекстовые индексы в PostgreSQL.
- Обновления в реальном времени через WebSocket.
- Готовые поля хранения OAuth-токенов и поддержку Google access token в существующих IMAP/SMTP-транспортах; полный Google consent/refresh flow требуется добавить в форк.
- Ограничение нагрузки на IMAP, задержки после отказов провайдера и режим периодического опроса через `IMAP_MAX_PERSISTENT_PER_HOST`.

## Что намеренно не разрабатывается для MVP

- Организации, рабочие пространства и таблицы членства в почтовых ящиках.
- Отдельные учётные записи или права MailExpert для каждого менеджера.
- Определение конкретного менеджера, выполнившего действие, на уровне приложения.
- Общая папка «Входящие» со всеми письмами из всех аккаунтов.
- Управление Postfix, Dovecot или EOP внутри процесса MailExpert.

Несколько менеджеров смогут входить с одинаковыми данными MailExpert и получать независимые сессии. Состояние почты будет общим: когда один менеджер помечает письмо прочитанным, перемещает или удаляет его, изменение видят остальные менеджеры, а MailExpert синхронизирует его с провайдером. Состояние интерфейса и выбранный ящик хранятся локально в браузере, поэтому менеджеры могут одновременно работать в разных ящиках.

Неустранимое ограничение общей учётной записи — отсутствие атрибуции. MailExpert будет видеть всех менеджеров как одного пользователя. Cloudflare Access может обеспечить отдельный вход на внешнем периметре и журналировать доступ, но внутри MailExpert почтовые действия всё равно будут записаны от имени общего пользователя. Если появится требование определять автора каждого действия, общую учётную запись нужно будет заменить моделью рабочего пространства и членства в ящиках, а не пытаться определять человека по IP-адресу.

## Развёртывание MVP

```text
Браузер менеджера
    |
    | HTTPS
    v
Cloudflare Access / обратный прокси
    |
    v
Веб-интерфейс MailExpert + серверная часть Node.js
    |             |             |
    |             |             +--> Redis (сессии)
    |             +----------------> PostgreSQL (аккаунты и кеш сообщений)
    +------------------------------> Gmail OAuth 2.0 + IMAP/SMTP
```

Создать двух пользователей MailExpert:

1. `system-admin` — администратор, используется только для развёртывания и настроек безопасности.
2. `team-mail` — общая рабочая учётная запись без прав администратора, которой принадлежат Gmail-аккаунты.

После создания пользователей открытую регистрацию необходимо отключить. Почтовые учётные данные хранятся в PostgreSQL в зашифрованном виде, поэтому ключ шифрования и резервные копии базы необходимо защищать совместно, но хранить раздельно.

## Базовая конфигурация

- ОС сервера: Ubuntu Server 24.04 LTS.
- Способ запуска: Docker Compose из репозитория.
- Node.js: версия 22 при запуске без Docker.
- PostgreSQL: версия 16 или новее.
- Redis: версия 7 или новее.
- Перед функциональными изменениями обновить все прямые backend/frontend-зависимости и lock-файлы до утверждённых актуальных версий, включая ImapFlow 2.x и Nodemailer 10.x; каждую несовместимую major-группу проверять отдельно.
- `IMAP_MAX_PERSISTENT_PER_HOST=15` для первого нагрузочного теста; это стартовая настройка, а не заявленный лимит Gmail.
- Gmail-аккаунты добавляются волнами: 10, затем 25, 50 и 100.
- Для разработки и production используются разные Google Cloud Projects. Режим `Testing` допускается только для разработки; рабочий пилот использует `In Production`, а выход на 100 аккаунтов требует завершённой Google OAuth verification, чтобы не упереться в пожизненный лимит 100 уникальных пользователей.
- У каждого Gmail-аккаунта установлено `include_in_unified_inbox=false`, то есть он исключён из общей папки «Входящие».
- Начальный интервал синхронизации — 60 секунд. Его нельзя уменьшать до успешного нагрузочного теста со 100 аккаунтами.
- Проверка TLS-сертификатов остаётся включённой.
- PostgreSQL и Redis не публикуются в интернет.

## Что необходимо изменить в форке MailExpert

### Обязательно до запуска со 100 аккаунтами

1. Выполнить полное контролируемое обновление backend/frontend-зависимостей и обоих `package-lock.json`, сначала зафиксировав зелёную базовую линию тестов. Несовместимые major-версии обновляются отдельными проверяемыми группами, без monkey patching и без подавления остающихся уязвимостей.
2. Добавить полноценный Google OAuth 2.0 flow: конфигурацию Client ID/Secret, state и PKCE, callback, проверку Google ID token, зашифрованное хранение refresh token, сериализованное обновление access token, повторное подключение и понятные состояния ошибок.
3. Добавить видимый фильтр ящиков в боковую панель. Существующая палитра команд уже умеет искать аккаунты, но постоянный фильтр проще для менеджеров и избавляет от прокрутки списка из 100 элементов.
4. Добавить фильтр состояния аккаунтов: подключён, синхронизируется, требует повторной OAuth-авторизации, ограничен провайдером или содержит ошибку. Используются существующие поля `last_sync` и `sync_error`.
5. Подготовить нагрузочный тест и инструкцию по поэтапному OAuth-подключению. До прохождения нагрузочного теста на целевом сервере нельзя утверждать, что система готова к 100 аккаунтам.

### Решается конфигурацией, а не кодом

1. Исключить импортированные аккаунты из общей папки «Входящие».
2. Использовать уже существующее запоминание последнего выбранного ящика в хранилище Zustand.
3. Использовать существующие алиасы и отдельную SMTP-маршрутизацию для каждого аккаунта.
4. Держать отдельную учётную запись администратора и отключить открытую регистрацию.
5. Поставить перед общей учётной записью индивидуальные аккаунты Cloudflare Access, если потребуется отдельно отзывать доступ менеджеров.

### Необязательно, после пользовательского тестирования

- Полностью скрыть кнопку общей папки «Входящие». Для первого пилота допустима пустая общая папка, поэтому это не блокирует выпуск.
- Запретить общей рабочей учётной записи менять настройки аккаунтов. Это понадобится, только если менеджерам нельзя разрешать добавлять, изменять или удалять учётные данные ящиков.
- Добавить отдельные личности менеджеров, журнал действий и членство в ящиках, если появится требование персональной ответственности.

## Подсистема собственных доменов и EOP

Нельзя помещать привилегированное управление почтовым сервером в Node.js-процесс MailExpert. При переходе к EOP добавляется отдельный почтовый контур:

```text
Исходящая почта:
MailExpert --SMTP 587--> Postfix --SMTP 25/TLS--> EOP --> интернет

Входящая почта:
интернет --> EOP --SMTP 25/TLS--> Postfix --> Dovecot/Maildir
                                             ^
                                             |
                                      MailExpert IMAP 993
```

MailExpert будет воспринимать каждый ящик Dovecot как обычный пользовательский IMAP/SMTP-аккаунт. Отдельный сервис подготовки ящиков или административное задание будет создавать домены, ящики, хеши паролей, алиасы и пути Maildir в базе, которую используют Postfix и Dovecot. Для первого запуска с EOP домен настраивается как Internal Relay, а неизвестные локальные получатели отклоняются Postfix. Переходить на Authoritative и DBEB следует только после синхронизации всех действительных получателей с Microsoft 365.

Этап EOP имеет отдельные критерии готовности и не должен блокировать Gmail MVP. Для него потребуются постоянный выделенный публичный IP, доступный входящий и исходящий TCP-порт 25, PTR/rDNS, TLS, коннекторы Microsoft 365, проверка лицензирования, а также SPF, DKIM и DMARC.

## Критерии готовности

Gmail MVP считается готовым, когда на целевом сервере подтверждены все условия:

- Десять одновременных браузерных сессий могут работать в разных ящиках под пользователем `team-mail`.
- Сто Gmail-аккаунтов подключены без циклических перезапусков и блокировки со стороны провайдера.
- Каждый Gmail подключён через Google OAuth, переживает истечение access token за счёт refresh token и показывает управляемое состояние повторной авторизации при `invalid_grant`.
- Менеджер может найти ящик по названию или адресу без прокрутки полного списка.
- Из выбранного Gmail-аккаунта можно читать, отправлять, пересылать, перемещать письма и отвечать на них.
- Изменение статуса прочтения или перемещение в одном браузере отображается в другом браузере и в Gmail.
- Ошибочные или ограниченные провайдером аккаунты находятся через единое представление состояния.
- После перезапуска MailExpert подключает аккаунты постепенно и не открывает 100 одновременных соединений с Gmail.
- Процедуры резервного копирования и восстановления PostgreSQL и Redis проверены.
- OAuth authorization codes, access/refresh tokens и почтовые пароли не появляются в логах, экспортируемых данных и сообщениях об ошибках.
